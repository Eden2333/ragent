# RAG 核心环节学习笔记

---

## 一、数据清洗（Data Cleaning）

### 1.1 是什么

- 对原始文档进行格式转换、噪声去除、结构化提取，将多源异构数据转化为可被 Embedding 模型准确表示的干净文本。

### 1.2 为什么需要

- 多源异构数据（PDF、Word、HTML、邮件等）格式各异，直接使用会引入大量噪声
- 文档中的页眉页脚、导航栏、水印、Logo 等非内容元素会干扰 Embedding 质量
- 编码不一致、特殊字符、重复内容会导致向量空间中语义漂移

### 1.3 主流方案

| 方案 | 说明 |
|------|------|
| **Apache Tika** | 支持 1000+ 文件格式解析，Java 生态首选 |
| **Unstructured.io** | 专为 RAG 设计的预处理框架，支持 PDF 表格、图片 OCR |
| **LangChain Document Loaders** | 100+ 数据源连接器，开箱即用 |
| **文本规范化** | Unicode 归一化、特殊字符移除、空白符合并 |
| **去重与去噪** | 移除重复段落、模板化内容（页眉页脚）、导航元素 |
| **元数据提取** | 保留标题、作者、日期、章节层级等结构信息 |
| **内容过滤** | 过滤低信息密度段落（目录、版权声明） |

### 1.4 技术难点

- **复杂版面解析**：扫描件 PDF、多栏排版、嵌套表格的精确提取仍是难题
- **多模态内容**：图表、流程图中的信息难以完整转化为文本
- **质量难以量化**：清洗效果通常只能通过下游检索效果间接评估
- **增量更新**：文档变更后如何高效增量清洗而非全量重处理
- **领域特异性**：金融报表、法律合同、医学文献各有专属格式规范，通用工具覆盖不全

## 二、分块（Chunking）

### 2.1 是什么

- 将长文档拆分为适合 Embedding 模型处理的短文本片段（chunk），每个 chunk 是向量检索的最小召回单位。

### 2.2 为什么需要

- Embedding 模型有 token 长度限制（通常 512~8192 tokens），长文档必须拆分
- 分块粒度直接影响检索精度：太大则噪声多，太小则丢失上下文
- 分块策略不同可导致召回率最多 9% 的差距，影响显著

### 2.3 主流方案

| 策略 | 原理 | 适用场景 |
|------|------|----------|
| **固定大小分块** | 按字符/token 数等长切割，设置 overlap | 快速原型、通用文本 |
| **递归分块（Recursive）** | 按段落→句子→字符层级递归切分 | 结构化文档，业界默认推荐 |
| **语义分块（Semantic）** | 基于 Embedding 相似度检测语义断点 | 知识库、技术文档，召回提升可达 70% |
| **结构感知分块** | 利用 Markdown 标题、HTML 标签、PDF 章节 | 有明确结构的文档 |
| **Late Chunking** | 先对全文编码再切分，保留全局上下文 | 长文档语义连贯性要求高的场景 |
| **Parent-Child 分块** | 小 chunk 用于检索，返回时附带父级大 chunk 上下文 | 兼顾精确召回与上下文完整性 |

**关键参数参考**：
- chunk size：512~1024 tokens（主流推荐）
- overlap：10%~20%（如 chunk 512 tokens，overlap 50~100 tokens）

### 2.4 技术难点

- **语义分块计算成本高**：其计算开销并不总能换来一致性的性能提升，需权衡
- **无通用最优策略**：代码、法律、对话等不同文档类型适配不同策略，需实验驱动
- **跨块信息丢失**：实体、引用关系可能被切断，需 overlap 或 Parent-Child 补救
- **表格与列表**：结构化内容被切分后语义破碎
- **多语言适配**：中文无空格分词、日韩语等的 token 计算与英文不同

## 三、索引（Indexing）

### 3.1 是什么

- 将文本 chunk 转为向量表示（Embedding）并存入向量数据库，同时可建立稀疏索引（BM25），使系统具备毫秒级语义检索能力。

### 3.2 为什么需要

- 向量索引使语义检索成为可能：即使用户用不同措辞提问，也能匹配到含义相近的文档
- 毫秒级检索要求高效的近似最近邻（ANN）算法
- 单一索引类型无法覆盖所有查询模式（精确术语匹配 vs 语义理解）

### 3.3 主流方案

**Embedding 模型**：

| 模型 | 特点 |
|------|------|
| OpenAI text-embedding-3-large | 3072 维，多语言支持好 |
| BGE / BGE-M3（智源） | 中文效果优秀，支持多粒度检索 |
| Voyage-3 | 新兴模型，检索基准表现突出 |
| Cohere embed-v3 | 支持 int8/binary 量化，降低存储成本 |
| GTE（阿里） | 中英双语，开源可本地部署 |

**向量数据库 & 索引算法**：

| 数据库 | 索引类型 | 特点 |
|--------|----------|------|
| Milvus | HNSW / IVF | 开源分布式，十亿级规模 |
| Qdrant | HNSW | Rust 实现，低延迟 |
| Pinecone | 托管服务 | Serverless，零运维 |
| PGVector | HNSW / IVF | PostgreSQL 扩展，复用现有基建 |
| Weaviate | HNSW | 内置混合检索 |

**索引算法对比**：
- **HNSW**：查询延迟低（~8ms），构建慢但查询快，生产环境首选
- **IVFFlat**：构建快但查询慢，适合数据频繁更新场景

**索引阶段增强（Index-time Enrichment）**：

在 chunk 入库前通过 LLM 对其进行二次加工，提升后续检索精度：

| 技术 | 核心思想 | 效果 |
|------|----------|------|
| **Hypothetical Questions（假设性问题生成）** | 为每个 chunk 预生成"该 chunk 可能被问到的问题"，将问题与 chunk 一起 Embedding 入库 | 检索时 query 直接与预设问题匹配，缩小 query-document 语义鸿沟，显著提升召回精度 |
| **摘要生成** | 为每个 chunk 生成简短摘要，作为额外索引维度 | 适合长 chunk 场景，摘要更易与 query 对齐 |
| **关键词/实体提取** | 提取 chunk 中的核心实体与关键词，补充元数据 | 增强精确匹配与过滤能力 |

Hypothetical Questions 与 HyDE 的区别：
- **Hypothetical Questions**：索引阶段为文档生成问题，作用于离线入库环节
- **HyDE**：查询阶段为 query 生成假设性答案再去检索，作用于在线查询环节
- 两者目标一致（拉近 query 与 document 在向量空间的距离），但作用时机和成本结构不同

### 3.4 技术难点

- **维度灾难**：高维向量（1536/3072 维）在超大规模数据集上索引性能退化
- **增量索引更新**：文档新增/删除后如何避免全量重建索引
- **Embedding 漂移**：更换模型版本后需重新编码全部文档
- **多租户隔离**：企业场景需在向量层面实现数据隔离与权限控制
- **成本控制**：大规模文档的 Embedding 调用费用 + 向量存储成本不容忽视

## 四、检索召回（Retrieval）

### 4.1 是什么

- 根据用户查询从索引中检索出最相关的文档片段（Top-K）作为生成上下文，是决定 RAG 回答质量上限的核心环节。

### 4.2 为什么需要

- 单纯向量检索存在"语义漂移"：语义相近但答案不相关的内容可能排在前面
- 精确术语（产品名、错误码）在向量空间中可能无法精确匹配
- 用户查询表述多样、模糊，需要查询理解与改写来弥补

### 4.3 主流方案

**检索策略**：

| 策略 | 原理 | 总结 |
|------|------|------|
| **向量检索** | 基于 Embedding 余弦相似度 Top-K | 语义理解强，精确匹配弱 |
| **BM25 关键词检索** | TF-IDF 变体的稀疏检索 | 精确术语匹配好，语义理解弱 |
| **混合检索（Hybrid）** | 向量 + BM25 结果融合 | 比单路检索 NDCG 提升约 7%，是生产环境主流 |
| **多路召回** | 从不同索引/策略分别召回再合并 | 提高召回覆盖率 |

**查询增强技术**：

| 技术 | 核心思想 |
|------|----------|
| **Query Rewriting** | LLM 重写原始查询，消除歧义和口语化表达 |
| **Multi-Query** | 将一个问题生成多个变体查询，扩大召回范围 |
| **HyDE** | 先让 LLM 生成假设性答案，用答案的 Embedding 去检索，缩小 query-document 语义差距 |
| **Step-back Prompting** | 将具体问题泛化为通用查询，检索更广的上下文 |

**结果融合**：
- **RRF（Reciprocal Rank Fusion）**：对不同排序列表做倒数排名融合，简单有效
- **加权融合**：根据查询类型动态调整向量/关键词权重

### 4.4 技术难点

- **查询理解不足**：口语化表达、多轮对话中的指代消解困难
- **长尾查询**：低频领域术语的 Embedding 质量差，检索失准
- **多跳推理**：需要从多个文档综合推理的问题，单次 Top-K 召回不够
- **实时性**：数据更新后检索结果的时效性难保障
- **融合权重调优**：混合检索超参数需针对具体数据集调优，缺乏通用方法

## 五、重排（Reranking）

### 5.1 是什么

- 对初步召回的候选结果（Top-50~100）进行精细化重新排序，筛选出最终送入 LLM 的 Top-K（3~10），是粗检索与生成之间的"精排"层。

### 5.2 为什么需要

- 向量检索（Bi-Encoder）为速度牺牲精度：query 和 document 独立编码，无法捕捉细粒度交互
- 生产中正确答案往往在 Top-50 内但不在 Top-5，需要精排把它提上来
- LLM 存在 "Lost in the Middle" 效应：上下文中间位置的信息容易被忽视，最相关的内容必须排到最前

### 5.3 主流方案

| 方案 | 原理 | 特点 |
|------|------|------|
| **Cross-Encoder** | 将 query-document pair 联合编码打分 | 精度最高，延迟较高（~100ms/对） |
| **ColBERT** | 延迟交互模型，token 级相似度聚合 | 精度接近 Cross-Encoder，可做首段检索，Recall@3 可提升约 4 个百分点 |
| **SPLADE** | 学习型稀疏表示 | 兼顾关键词匹配与语义理解 |
| **BGE-Reranker** | 智源开源 Cross-Encoder | 中文效果好，可本地部署 |
| **Cohere Rerank** | API 服务 | 即开即用，多语言支持 |
| **FlashRank** | 轻量级 Reranker | 适合延迟敏感场景 |
| **LLM-as-Reranker** | 用大模型直接做 listwise 排序 | 效果好但成本极高 |

**典型流程**：
```
向量检索 Top-100 → Cross-Encoder Rerank → Top-10 → 送入 LLM
```

**核心结论**：Cross-Encoder 重排是当前"成本最低、杠杆最高"的 RAG 优化手段。

### 5.4 技术难点

- **延迟开销**：Cross-Encoder 对每个 pair 独立推理，100 候选 = 100 次前向传播
- **域外泛化**：通用 Reranker 在垂直领域效果下降，往往需要微调
- **与上下文窗口协调**：Rerank 后保留多少 chunk 最优，需与 token 预算联合考量
- **训练数据稀缺**：高质量 query-document 相关性标注成本高
- **中文生态不成熟**：中文 Reranker 模型选择有限，英文生态更丰富

## 六、生成（Generation）

### 6.1 是什么

- 将检索并重排后的上下文与用户问题组合为 Prompt 送入 LLM，生成基于证据的最终回答，是 RAG 面向用户的输出环节。

### 6.2 为什么需要

- LLM 存在"幻觉"问题：没有外部知识约束时会编造事实
- RAG 通过提供可靠上下文来"接地"（Grounding）LLM 的回答
- 目标是让 LLM 基于检索到的证据回答，而非依赖参数记忆

### 6.3 主流方案

**Prompt 三层架构**：

| 层次 | 作用 | 关键要素 |
|------|------|----------|
| **System Prompt** | 定义模型行为规则 | 角色设定、回答约束、引用规则 |
| **Context** | 注入检索到的文档片段 | chunk 排列顺序、元数据标注 |
| **User Query** | 用户原始问题 | 可附加指令（如"只基于上下文回答"） |

**上下文管理策略**：
- **Token 预算分配**：为 context、system prompt、问题分别预留 token 额度
- **上下文压缩**：对召回 chunk 做摘要压缩后再注入，节省 token
- **上下文排序**：最相关的 chunk 放在最前和最后（应对 Lost-in-the-Middle 效应）

**引用溯源**：
- 为每个 chunk 标注来源编号，要求 LLM 在回答中标注引用
- 企业级方案通常强制要求回答必须基于检索内容，不可超出上下文范围

**幻觉缓解**：
- 指令约束："如果上下文中没有相关信息，请回答'我不知道'"
- 自我一致性检查：生成多个答案取共识
- Faithfulness 评估：度量答案对上下文的忠实度

### 6.4 技术难点

- **上下文窗口有限**：即使 128K 窗口，大量 chunk 堆砌仍会稀释注意力
- **幻觉无法完全消除**：即使提供了正确上下文，LLM 仍可能"创造性发挥"
- **多文档矛盾**：多个 chunk 之间存在矛盾时，模型难以判断取舍
- **回答可控性**：控制答案的详细程度、格式、风格仍需大量 prompt 工程
- **延迟与成本**：长上下文 → 更多 token → 更高延迟和费用
- **评估困难**：生成质量缺乏完美的自动化指标，Faithfulness / Answer Relevancy / Context Precision 等是当前主流度量维度
