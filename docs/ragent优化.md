# 项目现状与优化

## 现状
### 上下文是如何管理的
上下文是通过滚动摘要+最近N轮对话原文实现的。当对话总轮次超过设定值后会对最近N轮对话窗口外的内容进行压缩生成摘要，并且随着对话的不断进行，滑出最近N轮窗口的对话会和上一轮摘要生成新的摘要。
注意：压缩由LLM实现，新一轮的摘要由`上一轮摘要+滑出最近 N 轮对话窗口的原文` 压缩生成，而非每次都用原文来压缩；压缩的时机是Assistant回复后异步进行的。

#### 缺点
1. 只考虑的时间维度，越近的对话越容易进入上下文。应该综合考虑重要性、相关性以及近邻性。
- 重要性：与当前问题无关，如用户身份、喜好等重要性高；感谢等对话重要性低；
- 相关性：与当前问题有关，同一个对话历史会因当前问题的不同而有不同的相关性。
2. 只实现了原文、摘要的热区、温区分层，没有实现历史对话向量库（冷区），这导致系统的早期记忆薄弱：对话一旦滑出 N 轮原文窗口便不能再被召回（只能换出不能换入），仅靠摘要提供早期记忆过于模糊。
3. 可以缓存 问题-答案，类似问题直接查缓存减少调用LLM
4. 可以构建用户画像，如用户习惯、偏好、职业等。

### 意图识别是怎么做的？
系统构建了树形意图体系（DOMAIN,CATEGORY,TOPIC），用户的输入会连同 系统构建的意图体系一起发给LLM，LLM根据用户输入与不同意图的匹配度打分。
系统为评分设置了三挡阈值：低置信度（<0.4）；中置信度（[0.4, 0.6]）；高置信度（>0.6)。
- 如果存在高置信度意图：定向搜索目标意图绑定的知识库，topk取2；
- 如果全部是低置信度意图：全局搜索所有意图绑定的知识库，topk取3；
- 灰区置信度：定向搜索+全局搜索并行，但是这样消耗性能进行，有优化。

### 意图体系是如何组织和构建的？
> 扁平表建树+叶子结点平铺打分。
1. 意图节点表：意图节点的主要属性：
- kbId：知识库id；
- Level：DOMAIN/CATEGORY/TOPIC；
- parentId：父节点
- childIdList：子节点列表；

2. 建树
根据意图节点表构建意图树；并缓存意图树。

3. 叶子结点平铺打分
搜集意图树的叶子结点塞进 Prompt，过滤非叶子节点。

#### 缺点：
1. 使用了树形结构组织意图但没有做到逐层剪枝，树空有形在，白白浪费 “建树-平铺” 的性能开销。每次意图识别都将所有叶子结点塞进Prompt发给LLM，随着意图数量扩展LLM的打分噪声、token成本和延迟都会线性增加。

4. 是不是意图识别打分低的节点，其关联的Chunk进入rerank中的relevance_score也会比较低








## 优化
### 意图识别
#### 灰度区间搜索优化
- 原来：意图得分在0.4-0.6的置信度区间中，会触发定向搜索+全局搜索并行，但是这样消耗性能进行；
- 现在：先定向搜索，rerank时发现召回数量不够或者召回质量不高时才进行全局搜索，减少无必要的搜索。

#### 意图识别流程优化
- 原来：意图树的所有叶子结点平铺送入 LLM 打分，但随着意图数量扩展LLM的打分噪声、token成本和延迟都会线性增加。
- 现在：使用向量检索粗筛（JVM 缓存、余弦相似度匹配，当现有的意图节点变化时刷新缓存） + LLM 打分精筛的两级识别体系。当向量检索失败、粗筛节点 <= Top-K 时会走精筛兜底。
