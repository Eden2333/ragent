## 一、详版（项目经历主体）

**Ragent 企业级 RAG 智能问答平台**（基于开源项目 Ragent 二次开发与优化）｜后端开发｜2026.05 – 2026.11

**技术栈**：Java 17、Spring Boot 3.5、MyBatis-Plus、Milvus 2.6（HNSW 稠密向量 + BM25 稀疏向量）、Redis / Redisson、S3（RustFS）、Apache Tika、MCP（Streamable HTTP / JSON-RPC 2.0）、HikariCP、OpenAI 兼容协议 / SSE

**项目描述**：面向企业知识问答的 RAG 平台。主链路为「问题改写与拆分 → 树形意图识别 → 多通道检索 + Rerank → MCP 工具调用 → 流式生成」，模型层自建多供应商路由、三态熔断与首包探测，不依赖 Spring AI / LangChain4j。我基于开源项目 Ragent（作者 ding.ma，约 4 万行）进行二次开发，独立负责后端优化，主要解决三类问题：意图节点增多后识别成本和打分噪声上升；纯向量检索对精确词召回弱且灰区检索浪费资源；入库与多存储链路存在正确性缺陷。同时把平台接入公司内部大模型网关，并将 mcp-server 重构为按领域拆分的多 MCP Server 架构，接入只读 MySQL 工具服务。

**核心工作**：

1. **意图识别两级化（向量粗筛 + LLM 精筛）**
   - 问题：基线把意图树的全部叶子节点拼进 Prompt 交给 LLM 打分，节点越多，token 成本、延迟和打分噪声越高。
   - 方案：每个节点按「路径 + 说明」和每条示例问题分别生成向量，用最大余弦相似度召回 Top-10；再补入同名节点（保留跨系统同名意图的澄清引导）和全部 SYSTEM 节点（寒暄类短句向量不稳定），只把候选交给 LLM 精筛。
   - 工程细节：节点向量 L2 归一化后缓存在 JVM，用不可变对象 + `volatile` 整体替换；意图树变化时只对新增/变更文本调用 Embedding；重建用 `tryLock` 只放行一个线程，其余请求本次降级为全量打分；应用启动后异步预热。Embedding 失败、节点数不超过 Top-K、开关关闭时都回退原逻辑。
   - 效果：LLM 精筛的候选从「全部叶子节点」缩小到「≤10 个 + 同名/系统节点」，Prompt 长度不再随意图树规模线性增长。在 {{120}} 个叶子节点的意图树上，意图识别 Prompt token 减少 {{68%}}，P50 耗时由 {{1.6s}} 降至 {{0.9s}}，Top-1 意图准确率由 {{86%}} 提升至 {{91%}}。

2. **灰区检索：从「定向 + 全量并行」改为「定向先行、按需增量补全」**
   - 问题：意图最高分落在 [0.4, 0.6) 时，基线同时执行定向检索和全库检索，每次都要对所有知识库做向量检索。
   - 方案：先执行定向通道并走完去重和 Rerank，按「结果数 < topK 或 Rerank 最高分 < 0.6」判断召回质量，不达标才补全局检索；补检索时排除定向通道已查过的 collection，只查增量，再把两路结果合并重走后处理链。判断逻辑参考 CRAG「先评估检索质量、再决定是否纠正」的思路。
   - 效果：{{62%}} 的灰区请求定向召回即达标、不再触发全库检索，灰区检索 P50 耗时降低 {{38%}}；需要补检索时也不重复查询已覆盖的知识库。

3. **混合检索（BM25 + 稠密向量 + RRF 融合）**
   - 问题：纯向量检索对产品编号、错误码、专有名词这类需要字面匹配的问题召回弱。
   - 方案：利用 Milvus 2.6 的 BM25 Function，建表时为 `content` 开启中文分词，自动生成稀疏向量字段并建倒排索引，写入侧无需改代码；新增关键词检索通道，按 collection 并行检索，单库失败只告警跳过（兼容没有 BM25 字段的存量库）。
   - 融合：新增 RRF 后处理器，向量路与关键词路各自去重排名后按 `Σ w / (k + rank)` 融合，只用名次不用原始分（余弦分与 BM25 分量纲不同，BM25 分跨 collection 不可比），截断到 topK × 3 后进入 Rerank。通道开关、k 值、两路权重均配置化，默认关闭，可按知识库重建后灰度开启。
   - 效果：在 {{80}} 条编号、错误码、专有名词类测试问题上，Recall@10 由 {{61%}} 提升至 {{84%}}。

4. **文档入库链路统一与正确性修复**
   - 知识库「分块模式」绕开 Pipeline 引擎单独实现，且固定使用 Tika 解析。将其改为内存内置的默认流水线（Parser 按 MIME 自动选择解析器 → Chunker），复用 Pipeline 的节点日志和耗时统计，两种入库方式收敛为一条执行路径；Markdown 改由保留原始标记的专用解析器处理，供结构感知分块使用。
   - 向量写入处维度硬编码为 4096，切换 1024 维 Embedding 模型后写入失败：改为读取配置，并在创建知识库、修改 Embedding 模型时校验模型维度与向量库维度，把写入期才暴露的错误提前到配置阶段拦截。
   - Windows `\r\n` 换行导致结构感知分块下标错位：分块前统一归一化行尾。

5. **知识库跨 MySQL / S3 / Milvus 的一致性治理**
   - 问题：基线创建知识库时在 `@Transactional` 内先写 MySQL，S3 bucket 或 Milvus collection 创建失败无法回滚，留下孤儿资源；删除只做逻辑删除，外部资源泄漏，且 `collection_name` 唯一索引与逻辑删除冲突，同名知识库删除后无法重建。
   - 方案：创建改为「外部资源先建、MySQL 最后写」，任一步失败逐级补偿删除已建资源；删除改为先清 S3 与 Milvus、再删记录；插入改用 `INSERT ... ON DUPLICATE KEY UPDATE` 恢复已逻辑删除的记录；补偿失败时输出待人工清理的资源名。另修复 collection 名含下划线、不符合 S3 bucket 命名规则导致创建失败的问题。

6. **企业模型网关接入与模型层可观测（infra-ai）**
   - 新增内部大模型网关 Provider，实现 Chat / Embedding / Rerank 三个 OpenAI 兼容客户端，设为最高优先级候选，复用现有路由与熔断，百炼、SiliconFlow、Ollama 作为降级兜底；同时补齐基线缺失的百炼 Embedding 客户端。
   - 接入时逐项验证网关协议：Embedding 单批超过 10 条会挂起约 60s 后返回 500，客户端按 10 条分批；Rerank 为 Jina/Cohere 风格请求体，与百炼结构不同，单独实现；SSE 解析同时兼容 `reasoning_content` 与 `reasoning` 两种思考字段。
   - 用装饰器 `LoggingStreamCallback` 包在首包探测回调内层，记录每次调用的 provider / model、消息数、输出与思考长度、耗时，DEBUG 级截断记录输入输出，用于排查模型降级和慢调用。

7. **首轮对话体验优化**
   - 基线在首条消息写入会话时同步调用 LLM 生成标题，首字返回前多一次 LLM 往返。改为先写默认标题，再提交到独立线程池（TTL 透传上下文）异步生成；回写时带 `title = '新对话'` 条件，不覆盖用户已手动修改的标题；队列满时拒绝并告警，不影响主链路。新会话首问的首字延迟（TTFT）降低约 {{1.1s}}。

8. **MCP Server 重构：公共协议层 + 按领域声明式注册（mcp-server）**
   - 问题：原版只有一个无鉴权的 `/mcp` 端点，全局注册表自动发现所有工具 Bean，新增一个工具就对所有客户端可见，高风险工具无处安放。协议实现也有多处不合规（对原版逐项跑冒烟用例发现）：`tools/list` 输出 `enumValues` 而不是 JSON Schema 的 `enum`（Gson 注解在 Jackson 下不生效），客户端拿不到参数枚举值；成功响应带 `"error": null`、错误响应带 `"result": null`；不做版本协商，固定返回一个未发布的协议版本号；不支持 `ping`；通知返回 204 而不是 202；非法 JSON 返回 Spring 默认错误体而不是 JSON-RPC 错误；工具异常信息原样返回给客户端。
   - 方案：抽出公共协议层，一个通用端点按路径（`/mcp`、`/mcp/{领域}-mcp`）路由到对应 Server。每个领域只实现一个 `McpServerDefinition`，声明路径、工具集、`instructions`、鉴权策略和并发上限；版本协商（4 个修订版）、JSON-RPC 校验与标准错误码、按协商版本决定是否接受批量消息、通知返回 202、异常脱敏都只实现一次。原 `/mcp` 作为默认 Server 迁入，保留「实现 `MCPToolExecutor` 即自动注册」的扩展方式，主服务的 MCP 客户端无需改动。
   - 隔离与治理：
     - 工具隔离：领域工具只挂在声明它的 Server 上；某个类如果同时实现两种工具接口（会被自动暴露到无鉴权的 `/mcp`），直接阻止应用启动；路径、Server 名、工具名的格式和唯一性在启动时校验，不合规就拒绝启动。
     - 按 Server 鉴权：Bearer Token 鉴权抽成通用组件，常量时间比较，Token 绑定授权范围，占位值 Token 自动禁用，没有可用 Token 时拒绝所有请求。
     - 舱壁：每个 Server 用信号量限制同时执行的工具调用数，超限立即返回「繁忙」，避免一个领域占满 Web 线程拖垮其他领域。
   - 第一个领域：只读 MySQL Server（`/mcp/mysql-mcp`），提供数据源列表、表结构查询、只读 SQL 执行 3 个工具，用 `instructions` 引导模型先查表结构再写 SQL。分层防御：SQL 静态校验（剥离注释、字面量和标识符后限制单语句、首关键字白名单和写操作/锁/`SLEEP`/`INTO OUTFILE` 黑名单，拒绝可执行注释，宁可误拒）→ 只读连接 + `START TRANSACTION READ ONLY` + 执行后回滚 → 驱动强制关闭多语句和 `LOAD DATA LOCAL` → 30s 超时、行数上限与截断标记、单字段 10000 字符上限（控制返回给模型的上下文长度）→ 错误信息脱敏。
   - 验证：新增 116 个单元测试，覆盖协议处理、启动校验、鉴权、HTTP 端点，以及 SQL 校验器（20 条合法查询放行、49 条变更/绕过语句拒绝）；连接真实 MySQL 8 跑通 28 项 HTTP 冒烟用例；用主服务真实的 `HttpMCPClient` 调用重构后的 `/mcp`，初始化、列工具、调工具全部正常，且客户端开始能拿到参数枚举值。

## 三、面试深挖要点

| 可能被问 | 回答要点 |
|---|---|
| 向量粗筛已经排好序，为什么还要 LLM 精筛？ | 向量只衡量语义相近，分不清「这个意图能不能回答、该走哪个系统」；LLM 结合说明和示例判断更准。粗筛负责缩小范围、控成本，精筛负责准确。这与 Agent 工具很多时先做 Tool Retrieval 再让模型选工具是同一思路。 |
| 粗筛的 Embedding 为什么不走模型降级？ | 节点向量和问题向量必须来自同一模型、同一向量空间，换模型后相似度没有意义。所以 Embedding 失败时退回全量 LLM 打分，而不是换模型。 |
| 意图向量索引并发重建怎么处理？ | 索引是不可变 record，`volatile` 引用整体替换；`tryLock` 只让一个线程重建，其他请求本次降级、不阻塞；重建时按文本复用旧向量，只对增量文本调用 Embedding。 |
| RRF 为什么用名次不用分数？k=60 怎么来的？ | 余弦分和 BM25 分量纲不同，BM25 分在不同 collection 间也不可比，按名次融合最稳。k=60 是 RRF 论文的常用取值，用来压低头部名次差距对结果的影响；两路权重可配置。 |
| 灰区补检索的判定可靠吗？ | 已知局限：Rerank 降级到空实现时，分数变成相似度或 RRF 尺度，0.6 阈值几乎总会触发补检索。改进方向是按 Rerank 是否真实生效切换阈值，或改用相对分差判断。 |
| 为什么用补偿而不用分布式事务？ | S3 和 Milvus 不支持 XA；知识库创建是低频管理操作，按「难回滚的先做、可回滚的后做」排序再加补偿，成本最低。局限是补偿本身失败只能靠日志人工清理，后续可加定时对账任务。 |
| BM25 对存量知识库生效吗？ | 不生效。BM25 字段在建表时确定，存量 collection 需要重建并重新导入。所以关键词通道默认关闭，按库失败隔离，重建后再灰度开启。 |
| 这算 Agentic RAG 吗？ | 不算，仍是「固定管道 + 阈值分支」。灰区补检索只借鉴了 CRAG「评估后纠正」的思路，没有让模型自主决定检索轮次。下一步方向：原生 function calling、把检索做成有轮数上限的工具循环、建立离线评测集作为改动的验收依据。 |
| MySQL MCP 只靠 SQL 黑名单够吗？ | 不够，静态校验只是第一层，绕过手法很多（可执行注释、多语句、`sql_mode` 差异）。后面还有只读连接 + 只读事务 + 回滚、驱动层禁多语句和 LOCAL INFILE、超时和行数上限。生产环境还应给 MCP 单独配只读数据库账号。 |
| 工具执行失败为什么不返回 JSON-RPC error？ | MCP 区分协议错误和工具执行错误。方法不存在、参数格式错是协议错误，用 JSON-RPC error；SQL 校验不通过、查询超时是工具错误，放在 result 里并标 `isError: true`，模型能读到原因并改写 SQL 重试。 |
| 为什么把 MCP Server 拆成 `/mcp/{领域}-mcp`？ | ① 工具隔离：高风险工具只出现在有鉴权的端点上，新加工具不会顺带暴露；② 权限：每个领域可以用不同的 Token 和授权范围；③ 模型侧：客户端只连需要的领域，`tools/list` 只返回少量相关工具，描述占的 token 更少，选错工具的概率更低，和意图识别先做向量粗筛是同一个思路；④ Prompt 注入的影响范围：一个会话没连上的高危工具，注入内容也调不到；⑤ 各领域可以独立演进，端点边界也是将来拆独立服务的边界。 |
| 公共协议层怎么设计？新增一个领域要做什么？ | 协议层负责路由、鉴权调度、HTTP 头校验、版本协商、JSON-RPC 校验与错误码、批量消息、舱壁和异常脱敏。领域只实现一个 `McpServerDefinition`，再加上工具类（实现 `McpTool`）。启动时注册表校验路径、名称和工具名，有冲突就拒绝启动。 |
| 同一个进程里多个 Server，怎么避免互相拖垮？ | 每个 Server 一个信号量做舱壁，用非阻塞的 `tryAcquire`，超限立即返回「繁忙」，不让请求在 Web 线程里排队。局限：只限并发不限速率，各 Server 仍共享 JVM 和内存，高风险领域最终应拆成独立进程。 |
| 原版 `/mcp` 的协议问题是怎么发现的？ | 重构前先对原版跑一遍冒烟用例，逐项对照 MCP 规范和 JSON-RPC 2.0 规范。最严重的是 `enum` 字段名错误：主服务的客户端拿不到参数枚举值，参数抽取时模型看不到可选值。重构后用主服务真实的 `HttpMCPClient` 回归验证，确认已经修复。 |
| 这个 MCP Server 有什么局限？ | 只实现了 POST 请求-响应，不提供 SSE 流和会话管理；只支持基于 `initialize` 握手的修订版（到 2025-11-25），没有适配 2026-07-28 版改成的「无握手、每个请求自带版本」模式；Token 是静态配置，不能轮换，也没有接入 OAuth 2.1；查询审计只写日志；主服务的 MCP 客户端会自动补 `/mcp` 后缀且不带 `Authorization` 头，还不能调用需要鉴权的领域 Server。 |
| 效果数据怎么测的？ | 说清测试集规模、对照方式（开关 A/B 或 main vs refine）和统计口径，见第四节。说不出口径的数字不要写。 |
