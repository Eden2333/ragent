# 管理后台意图节点配置最佳实践

基于 `DefaultIntentClassifier` 的工作原理（将所有叶子节点的 description + examples 拼成 Prompt 发给 LLM 打分），配置质量直接决定了意图识别的准确率。

---

## 一、核心字段配置原则

### 1. description（描述）— 最关键的字段

LLM 分类器在构造 Prompt 时，会把 description 作为每个叶子节点的核心语义描述发给模型。

**配置要点：**

- 用一句话概括"这个节点覆盖什么类型的问题"，面向 LLM 而不是人
- 强调**边界**——不仅说"是什么"，还要暗示"不是什么"
- 避免含糊笼统的描述（如"相关问题"）

**好的示例：**

```
招聘流程、面试安排、校招社招、Offer 发放、入职手续等人才获取相关问题。
不包含入职后的转正、绩效、薪资等。
```

**差的示例：**

```
招聘相关问题
```

### 2. examples（示例问题）— 第二关键字段

LLM 依赖示例来理解"这个节点到底是什么语义范围"。

**配置要点：**

- 每个叶子节点 **3-5 条** 示例为最佳（过少语义不够，过多稀释重点）
- 示例必须**多样化**——覆盖不同问法、口语化表达、同义词
- 包含 **边界案例**——容易和其他节点混淆的问法
- 一行一条，不加序号

**好的示例：**（以"考勤制度"节点为例）

```
迟到了会有什么处罚？
正常上班时间是几点到几点？
忘记打卡怎么办？
加班到很晚第二天能晚到吗？
年假是怎么计算的？
```

注意第 4 条故意用口语化表达，第 5 条覆盖了"假期"边界。

**差的示例：**

```
请问考勤规定是什么？
考勤规定
考勤
```

（过于同质，对 LLM 理解边界没帮助）

### 3. intentCode（意图标识）— 命名规范

虽然不影响 LLM 分类，但影响可维护性和调试效率。

**推荐命名规范：**

```
{domain}-{category}-{topic}
```

例如：`group-hr-attendance`、`biz-oa-security`、`mcp-sales-data`

## 二、层级结构设计原则

基于三层结构（DOMAIN → CATEGORY → TOPIC）：

| 层级 | 定位 | 配置原则 | 是否挂资源 |
|------|------|---------|-----------|
| DOMAIN | 业务域（集团信息化、业务系统） | 只需 name，description 可选 | ❌ 不挂（除非整域只有一个 Collection） |
| CATEGORY | 业务分类（人事、IT支持） | 需 description + examples | 可挂（如果不再细分 TOPIC） |
| TOPIC | 具体场景（发票查询、架构设计） | 必须有详细 description + examples | ✅ 必须挂 |

**核心原则：只有叶子节点参与 LLM 打分。**

所以：

- 如果一个 CATEGORY 下面**没有 TOPIC 子节点**，那它本身就是叶子，必须配好 description 和 examples
- 如果一个 CATEGORY 下面**有 TOPIC**，那 CATEGORY 自身的 description 只起"给人看的分组说明"作用，不参与 LLM 打分

## 三、不同 Kind 的配置差异

### KB（知识库检索）节点

| 字段 | 必填 | 说明 |
|------|------|------|
| description | ✅ | 面向 LLM 的语义描述 |
| examples | ✅（叶子） | 3-5 条多样化示例 |
| kbId/collectionName | ✅ | 对应的 Milvus Collection |
| topK | 可选 | 特定场景需要更多/更少检索结果时覆盖全局值 |
| promptTemplate | 可选 | 需要定制化回答格式时填写（如发票信息格式化） |
| promptSnippet | 可选 | 多意图命中时的补充规则 |

### MCP（工具调用）节点

| 字段 | 必填 | 说明 |
|------|------|------|
| description | ✅ | 描述"什么问题应该调用这个工具" |
| examples | ✅ | 示例应覆盖用户可能触发工具调用的各种问法 |
| mcpToolId | ✅ | 必须与 MCPToolRegistry 中注册的 toolId 一致 |
| promptTemplate | 推荐 | 工具返回 JSON 后如何格式化给用户 |
| paramPromptTemplate | 推荐 | 从用户问题中提取工具参数的提示词 |

### SYSTEM（系统交互）节点

| 字段 | 必填 | 说明 |
|------|------|------|
| description | ✅ | 如"用户与助手打招呼"这类简短说明 |
| examples | ✅ | 覆盖各种寒暄/系统类表达 |
| promptTemplate | 可选 | 一般不需要，系统逻辑硬编码处理即可 |

## 四、避免意图混淆的配置技巧

在当前项目中，`DefaultIntentClassifier` 的 Prompt 构建逻辑会把所有叶子节点一次性列给 LLM。当两个节点语义接近时，LLM 容易打出相近分数，导致路由不稳定。

### 解决方法

**1. 在 description 中写明"不是什么"**

```
// group-hr（人事）
description: 招聘、入职、转正、离职、绩效、薪资、考勤、请假等人力资源相关问题。
             不包含公司的通用规章制度、行为规范等（那些归入 POLICY）。
```

**2. 在容易混淆的节点之间，用 examples 做"锚定"**

如果"考勤"和"规章制度"容易混淆：

- 考勤 examples 加一条：`"迟到罚款属于考勤处理还是违纪处理？"` → 锚定到考勤
- 规章制度 examples 加一条：`"员工手册中对保密义务是怎么规定的？"` → 锚定到制度

**3. 控制叶子节点总数不超过 20-25 个**

当前项目中 LLM 是一次性对所有叶子打分。经验上：

- < 15 个叶子：效果很好
- 15-25 个叶子：需要写好 description 来区分
- \> 30 个叶子：建议改为分层识别（先识别 Domain，再在 Domain 内识别 Topic）

## 五、Prompt 模板的配置时机

不是每个节点都需要 promptTemplate。只有以下场景才需要配：

| 场景 | 是否配 promptTemplate | 原因 |
|------|---------------------|------|
| 常规问答（如"考勤规定是什么？"） | ❌ | 用全局默认模板即可 |
| 有格式化要求（如发票信息查询） | ✅ | 需要控制输出格式 |
| MCP 工具返回值展示 | ✅ | 需要将 JSON 转为自然语言 |
| 需要特定角色/语气 | ✅ | 如法律顾问、技术专家人设 |

`promptSnippet` 适合轻量级规则补充，如：

```
注意：如果用户问的是具体某人的考勤记录而非制度规定，请告知需要在 OA 系统查询。
```

## 六、配置模板参考

以新增一个"差旅报销"场景为例：

```
节点名称:     差旅报销
意图标识:     group-finance-travel
层级:         TOPIC
父节点:       group-finance（财务）
类型:         KB
知识库:       [选择财务知识库]
描述:         差旅费用报销的标准、流程、所需材料、审批时限等相关问题。
              不包含普通办公用品报销或项目预算问题。
示例问题:
  出差坐高铁能报销吗？
  报销需要提供哪些票据？
  国内出差住宿标准是多少？
  报销审批一般需要几天？
  出差补贴怎么算的？
TopK:         留空（使用全局默认）
排序:         10
启用:         ✅
```

## 七、总结

配置质量从高到低的影响因子：

1. **description 写得是否面向 LLM、是否划清边界** — 决定 60% 的识别准确率
2. **examples 是否多样化、是否覆盖口语化表达** — 决定 25% 的准确率
3. **整棵树的结构是否合理（叶子数量适中、层级清晰）** — 决定 10% 的稳定性
4. **promptTemplate / promptSnippet** — 不影响识别，但影响最终回答质量
