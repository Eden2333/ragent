## 详版

### Ragent — 企业级 RAG 智能问答系统（后端）

**技术栈**：Java 17、Spring Boot 3.5、MyBatis-Plus、Milvus 2.6、Redis + Redisson、Apache Tika、Sa-Token、S3 兼容存储、Maven 多模块

**项目描述**：从零自研的企业级检索增强生成（RAG）问答系统后端，覆盖文档入库到智能问答全链路。采用 `framework`（通用基础设施）/ `infra-ai`（模型供应商抽象）/ `bootstrap`（业务）三层 Maven 多模块架构，约 4 万行 Java 代码、400+ 源文件、20+ 业务表。未依赖 Spring AI / LangChain4j，自建 AI 能力抽象层以规避框架版本迭代带来的重写成本。

**核心职责与产出**：

- **多通道检索引擎**：设计「意图定向检索 + 全局向量检索」双通道并行架构，基于 Milvus（HNSW + COSINE）做向量 ANN 检索；检索结果经去重、重排序等后处理器链逐级精炼。通道与后处理器均面向 `SearchChannel` / `SearchResultPostProcessor` 接口编程，新增通道实现接口即自动生效。
- **重排序（Rerank）**：接入阿里云百炼 Rerank 精排服务，通过模型路由在供应商不可用时自动降级到空实现，保证检索链路不中断。
- **查询改写与意图路由**：实现 LLM 驱动的查询改写 + 多子问题拆分（携带历史做多轮指代消解）+ 领域术语归一化；构建树形意图体系（领域→类目→话题），用 LLM 结构化打分对叶子意图节点评分并按阈值路由到知识库检索 / MCP 工具 / 直接问答；意图得分接近时主动触发歧义澄清，避免硬猜。
- **模型路由与三态熔断**：为每个模型维护独立的 CLOSED→OPEN→HALF_OPEN 三态熔断器，失败达阈值自动熔断、冷却后半开探测恢复；配合优先级降级链实现多供应商（百炼 / SiliconFlow / Ollama）自动切换，业务层无感知。SSE 流式输出引入首包探测缓冲，确保模型切换时用户端不收到半截脏数据。
- **分布式队列限流**：基于 Redis 信号量 + ZSET 有序队列 + Pub/Sub 通知实现跨实例排队限流，用 Lua 脚本原子判断队头窗口，许可自动过期防死锁，本地合并通知规避惊群，排队状态全程 SSE 推送。
- **文档入库流水线**：基于节点编排的 Pipeline 架构，串联文档解析（Apache Tika）→ LLM 富集（关键词/摘要）→ 分块 → 向量化 → 写入 Milvus；提供固定长度、结构感知（Markdown）、句子、段落 4 种分块策略，工厂模式按枚举装配，节点级执行日志可精确定位失败环节。
- **工程基础设施**：封装三级异常体系 + 统一异常拦截、双维度幂等、Snowflake 分布式 ID、用户/Trace 上下文跨线程透传（`TtlExecutors` 包装 8 个按负载隔离的线程池）；基于 AOP（`@RagTraceNode`）实现改写/意图/检索/生成全链路耗时与输入输出追踪。

## 精简版（3-4 条，适合空间有限的简历）

**Ragent — 企业级 RAG 智能问答系统（后端）** · Java 17 / Spring Boot 3.5 / Milvus / Redis / Sa-Token

- 从零自研 RAG 问答后端，三层 Maven 多模块架构（framework / infra-ai / bootstrap），约 4 万行代码；自建模型能力抽象层，不绑定 Spring AI。
- 设计意图定向 + 全局向量双通道并行检索引擎 + 可插拔后处理器链（去重、百炼 Rerank 精排），面向接口编程支持检索通道/后处理器零改动扩展。
- 实现 LLM 查询改写与多子问题拆分、树形意图识别与阈值路由（知识库/MCP 工具/直接问答）及歧义澄清，提升复杂与多轮问题的检索准确率。
- 构建模型多供应商路由 + 三态熔断降级 + SSE 首包探测，保障模型故障下服务可用与流式输出无脏数据；基于 Redis(ZSET+信号量+Lua) 实现分布式队列限流。

## 面试追问预案（⚠️ 重要）

简历写得越亮眼，面试越会深挖。基于真实代码边界，提醒几个坑：

| 若被问到 | 诚实且加分的回答方向 |
|---|---|
| 是不是 Agentic RAG？ | 不要自称 Agentic。实话说是「固定管道 + 意图路由 + 工具分支」的增强版 RAG，能清楚讲出与 Self-RAG/CRAG（检索质量自评、迭代重检索）的差距，反而显专业。 |
| 混合检索怎么做的？ | 当前是纯向量双通道（定向 vs 全局），没有 BM25/稀疏向量混合与 RRF 融合。可讲成「已识别精确匹配类查询召回弱，混合检索是下一步 P0 优化」。 |
| 入库富集的 keywords/summary 怎么用于检索？ | 诚实说目前富集结果存入 metadata 但检索侧未消费，属已知待优化点。切勿吹成「提升召回」。 |
| 用了哪些分块高级策略？ | 只有固定/结构感知/句子/段落 4 种，没有父子分块 / 语义分块 / Late Chunking。 |

建议：把「下一步优化（混合检索 + RRF、CRAG 迭代重检索）」当作主动亮点来讲，展示对 RAG 技术全景和边界的清醒认知——这比假装全都做了更能打动面试官。
